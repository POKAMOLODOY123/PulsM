# Подготовка проекта к внедрению в web-приложения

**Статус:** приложение готово к внедрению: обучение (train), инференс (API) и Docker-образ проверены.

## Рекомендация: Docker + REST API

Оптимальный вариант для интеграции с веб-приложением — **вынести инференс в отдельный REST API и запускать его в Docker**.

### Почему так

| Подход | Плюсы | Минусы |
|--------|--------|--------|
| **Docker + API (рекомендуется)** | Одинаковое окружение везде, веб-сервер только дергает HTTP; легко масштабировать и деплоить | Нужно один раз настроить образ и API |
| Только Docker (без API) | Уже есть Dockerfile | Текущий образ тяжёлый (CUDA, Jupyter), нет точки входа для «запрос → ответ» |
| Без Docker (скрипт по HTTP) | Проще на старте | Разные версии Python/пакетов на серверах, сложнее воспроизвести окружение |
| Serverless (Lambda и т.п.) | Не нужно крутить сервер | Холодный старт, ограничения по памяти/времени, пакет с моделью и зависимостями |

Итого: **Docker** даёт предсказуемое окружение и упрощает деплой на любой хостинг; **REST API** даёт веб-приложению одну точку входа: «отправил данные — получил число упаковок и сегменты».

## Что сделать по шагам

### 1. REST API для инференса

- **Технология:** FastAPI (лёгкий, автодокументация по `/docs`, асинхронность при необходимости).
- **Назначение:** загрузка обученной модели и конфига при старте; один (или два) эндпоинта:
  - **Вариант A:** `POST /predict` — тело: `{ "file_id": "1025" }` — сервер сам читает серию из `data/raw/series/1025.txt` и возвращает результат.
  - **Вариант B:** `POST /predict` — тело: `{ "speed": [10.2, 0, 15.1, ...] }` — предсказание по переданному массиву скорости (удобно, если веб-приложение само получает данные с датчиков).
- **Ответ:** например `{ "count": 29, "segments": [[120, 450], [500, 890], ...] }` — число упаковок и границы сегментов по индексам (или по времени, если договориться о формате).

В репозитории добавлен минимальный каркас API в папке `api/` (см. ниже).

### 2. Отдельный Docker-образ для API

- **Зачем отдельный:** текущий `Dockerfile` заточен под разработку (CUDA, Jupyter, Conda). Для веб-инференса достаточно лёгкого образа без GPU.
- **Содержимое:** базовый образ `python:3.10-slim`, установка зависимостей только для инференса (pandas, numpy, scikit-learn, joblib, pyyaml, fastapi, uvicorn), копирование кода и обученной модели, запуск `uvicorn api.main:app`.
- **Модель и конфиг:** при сборке образа копировать `models/best_rf_model.joblib` и `configs/config.yaml` (или монтировать том при запуске, если модель обновляется отдельно).

В проекте добавлен пример такого образа: `Dockerfile.api` и `requirements-api.txt`.

### 3. Как веб-приложение будет использовать

- Веб-бэкенд (Node, Python, Go и т.д.) при необходимости подсчёта упаковок делает HTTP-запрос к API PackingTS, например:
  - `POST http://packing-api:8000/predict` с телом `{ "file_id": "1025" }` или `{ "speed": [...] }`.
- Получает JSON с `count` и `segments` и дальше использует их в своей логике (сохранение в БД, отображение в интерфейсе и т.п.).

### 4. Деплой

- **Перед сборкой образа** нужно один раз обучить модель: `python scripts/train.py` (из корня PackingTS-main), чтобы появился файл `models/best_rf_model.joblib`.
- **Локально:** из корня проекта выполнить:
  ```bash
  docker build -f Dockerfile.api -t packing-api .
  docker run -p 8000:8000 packing-api
  ```
  Документация API: http://localhost:8000/docs
- **Вместе с веб-приложением:** в `docker-compose.yml` описать два сервиса — ваш веб-сервер и `packing-api`; веб обращается по имени сервиса, например `http://packing-api:8000`.
- **Облако:** любой хостинг с поддержкой Docker (AWS ECS, Azure Container Instances, Yandex Cloud, собственный сервер с Docker) — образ один и тот же.

## Альтернативы

- **Только Docker без отдельного API:** если веб-приложение на Python и готово импортировать код проекта — можно вызывать функцию инференса напрямую внутри одного процесса. Минус: жёсткая связка версий и окружения с веб-фреймворком.
- **Один общий Dockerfile:** можно добавить в текущий образ установку FastAPI/uvicorn и запуск API по умолчанию (или по переменной окружения). Тогда один образ и для ноутбуков, и для API, но образ остаётся тяжёлым из-за CUDA и Conda.
- **Serverless:** вынести инференс в AWS Lambda / Yandex Cloud Functions и вызывать по HTTP. Имеет смысл, если запросов мало и важна экономия на простаивающем сервере; нужно упаковать модель и зависимости в архив и учесть лимиты по времени выполнения и памяти.

Если опишете, где планируете запускать веб-приложение (свой сервер, облако, только локально), можно сузить вариант деплоя и при необходимости дописать пример `docker-compose.yml` или команды для облака.
