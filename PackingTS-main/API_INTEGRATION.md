# Документация интеграции: Rust‑сервер ↔ сервис алгоритма (PackingTS)

## 1) Что это за интеграция

Алгоритм подсчёта упаковок (модель + постпроцессинг) реализован в Python и запускается как **отдельный HTTP‑сервис**.  
Основной веб‑сервер (на Rust) общается с ним по сети: **HTTP запрос → JSON ответ**.

Зачем это нужно:
- Rust‑приложение не тянет внутрь себя Python/ML‑зависимости.
- Python‑сервис можно масштабировать и обновлять отдельно.
- Контракт простой: один запрос на инференс, один JSON‑ответ.

Файлы реализации в проекте:
- `api/main.py` — FastAPI приложение (эндпоинты `/health`, `/predict`)
- `api/inference.py` — загрузка модели/конфига, построение признаков, инференс, постпроцессинг
- `Dockerfile.api`, `requirements-api.txt` — лёгкий образ для запуска API инференса

---

## 2) Схема взаимодействия (высокоуровневая)

1. Rust‑backend получает запрос от клиента/системы (например: “посчитать упаковки для файла 1025”).
2. Rust‑backend формирует HTTP запрос в сервис алгоритма:
   - либо по `file_id` (сервис сам читает исходный ряд из файла),
   - либо отправляет массив `speed` напрямую.
3. Python‑сервис:
   - загружает модель `models/best_rf_model.joblib` и конфиг `configs/config.yaml` (один раз),
   - строит признаки из скорости,
   - вычисляет вероятности,
   - постпроцессит в сегменты,
   - возвращает JSON: количество и сегменты.
4. Rust‑backend использует результат: сохраняет в БД, отдаёт на фронт, строит отчёт и т.д.

---

## 3) Базовый URL и формат данных

### Base URL
Внутри docker-compose обычно будет так:
- `http://packing-api:8000`

Локально (без Docker):
- `http://127.0.0.1:8000`

### Важные определения
- **speed**: временной ряд скорости (массив чисел).
- **segment**: отрезок `[start, end]` в индексах массива `speed`.
  - `start` и `end` — **целые индексы**
  - границы **включительные**
  - единица измерения: “номер точки ряда”, не секунды

## 4) API контракт

### 4.1 `GET /health`
Проверка доступности сервиса (liveness/readiness).

**Response (200):**
```json
{ "status": "ok" }
```

---

### 4.2 `POST /predict`
Основной метод инференса.

#### Request JSON
Нужно передать **ровно одно** из полей:

**Вариант A (по файлу):**
```json
{ "file_id": "1025" }
```

**Вариант B (по данным напрямую):**
```json
{ "speed": [12.3, 0.0, 15.1, 18.9] }
```

#### Семантика `file_id`
Если передан `file_id`, сервис читает файл:
- путь берётся из `configs/config.yaml` → `paths.series_dir`
- фактический файл: `{series_dir}/{file_id}.txt`

Файл должен содержать колонку скорости (по конфигу `data.target_col`, сейчас `Speed_2`).

#### Response JSON (200)
```json
{
  "count": 19,
  "segments": [
    [720, 1811],
    [2036, 3155]
  ]
}
```

- **count**: целое число найденных “упаковок” (событий)
- **segments**: список событий, каждое событие — `[start, end]`

#### Ошибки
- **400 Bad Request**
  - не передано ни `file_id`, ни `speed`
  - переданы и `file_id`, и `speed` одновременно
  - `speed` пустой
- **404 Not Found**
  - указан `file_id`, но соответствующий файл `{file_id}.txt` не найден
- **500 Internal Server Error**
  - ошибка при загрузке модели/конфига, построении признаков, инференсе и т.п.

## 5) Пример вызова из Rust (reqwest + serde)

Вариант “по file_id”.

```rust
use reqwest::Client;
use serde::{Deserialize, Serialize};

#[derive(Serialize)]
struct PredictRequestByFile<'a> {
    file_id: &'a str,
}

#[derive(Deserialize, Debug)]
struct PredictResponse {
    count: i64,
    segments: Vec<[i64; 2]>,
}

pub async fn predict_count(file_id: &str) -> anyhow::Result<PredictResponse> {
    let client = Client::new();
    let url = "http://packing-api:8000/predict"; // имя сервиса в docker-compose

    let resp = client
        .post(url)
        .json(&PredictRequestByFile { file_id })
        .send()
        .await?
        .error_for_status()? // 4xx/5xx → ошибка
        .json::<PredictResponse>()
        .await?;

    Ok(resp)
}
```

Рекомендации со стороны Rust:
- ставить **таймаут** на запрос (например 5–30 секунд; зависит от SLA)
- логировать `status code` и тело ошибки при 4xx/5xx
- при 500 можно делать ограниченный ретрай (если это инфраструктурная ошибка)

## 7) Производительность и ресурсы (коротко)

### Что происходит на запросе (CPU‑нагрузка)
Основная стоимость запроса:
1) построение признаков (rolling‑статистики по окнам)  
2) `RandomForest.predict_proba`  
3) постпроцессинг сегментов

### Что уже оптимизировано
- модель и конфиг загружаются **один раз**, а не на каждый запрос
- для инференса принудительно используется **`n_jobs=1`** (стабильно в Docker/Windows)

### Как масштабировать
Если нужно больше запросов в секунду:
- поднимать несколько экземпляров сервиса (несколько контейнеров) и балансировать
- или запускать несколько воркеров uvicorn (в зависимости от окружения)
